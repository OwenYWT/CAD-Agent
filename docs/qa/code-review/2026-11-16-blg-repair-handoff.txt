一、线上原始证据和根因

1. 任务 e3fc8d2e-36c1-4203-b9d1-9d1ad7f273a2

从实际持久化记录读取到三版 API 计划，依次出现 Unknown document 'Model'、makeBox 参数类型错误、导出 BLG_Solid 不存在。
最终计划 source_id=0be97cc3-6d44-4781-b4c2-e81f1da04e57 已正确创建内部名称 BLG_Solid 并设置同名 Label；不能归因为只设置 Label。
运行器却把传入文档保存为 input.FCStd，子进程打开后 Name 为 input。脚本找不到 Model，另建 Model 并在其中建模；运行器最后保存的是原来的空 input 文档。
object_not_found 又未被纳入结构化错误分类，最终成为 internal，无法进入工作流已有的模型修复流程。

2. 任务 0b2ccb59-577b-4790-92bd-95b7037a7e1a

原始 BSketch 由重叠矩形组成，pad-b 返回 profile_geometry_invalid。模型替换为单一轮廓后，b-cstr-d10 出现冗余约束。
两次失败属于同一 BSketch、同一消费特征 pad-b，但错误类别由 profile 变为 constraint，旧进度判断认为执行退回到早前操作，在 1/8 次修复后停止。
轮廓替换后的 B 草图确有冗余尺寸；FreeCAD 的拒绝是正确的。应用错误是提前禁止正常约束修复，而不是求解器应该接受冗余约束。

二、业务代码修改（仅五个文件）

backend/sandbox/freecad_api.py
  使用实际 document.Name 生成子进程输入文件名，保留传入文档身份。
  单独保存脚本执行命名空间，避免脚本重新绑定 document 后绕过原有身份检查。
  已覆盖不同文档名、载入已有 FCStd 后继续 API 操作、GUI、Spreadsheet 表达式、布尔操作和失败脚本回滚。

backend/sandbox/freecad_entry.py
  object_not_found 附带请求对象、实际文档名以及现有对象 Name/Label，供已有修复链路使用。
  仍按内部 Name 查找，不用 Label 猜测替代对象。

backend/app/execution/podman_backend.py
  object_not_found 归入 user_code，允许已有工作流发起模型修复；不作为基础设施故障自动重试。

backend/app/workflows/native_repair.py
  允许同一草图、同一消费特征从 profile 错误进入 constraint 修复。
  不提前宣告该特征已成功；仍保留重复物理状态检查、单目标预算、总预算以及真实回退检查。

backend/app/workflows/agent_v2.py
  通过 agent-v2-profile-constraint-handoff-v1 Temporal 标记启用新行为，保证旧历史按原决策回放。
  该开关只服务于持久工作流历史，不是新增用户配置或另一套业务入口。
