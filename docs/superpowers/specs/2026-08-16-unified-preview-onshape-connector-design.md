# Unified Preview and Durable Onshape Connector Design

## Status

Approved in conversation on 2026-08-16. This document defines the product and
architecture boundary only. It does not authorize a second non-durable write
path or any simulated CAD result.

## Goal

Provide one mechanical-design workspace that works for three user modes:

1. native CAD-Agent projects generated and modified by Durable Agent V2;
2. user-owned Onshape projects read and modified through OAuth;
3. real, quota-limited guest projects for users who have not connected Onshape.

All modes show a real model preview, parameters, proposed changes, task progress,
validation evidence, and an explicit apply or accept action. A preview artifact
is always a derived view of authoritative CAD state, never the editable source
of truth.

## Product boundary

### Native mode

- `ProjectRevision` is authoritative.
- Generation and modification run through `McadAgentWorkflowV2` and
  `ExecutionBackend`.
- Candidate artifacts are rendered in the existing Three.js workspace.
- Required validation seals the native candidate before review, exactly as in
  the existing V2 lifecycle. Accepting a reviewable Change Set advances the
  branch through existing compare-and-swap rules; the unified UI introduces no
  second sealing action or path.

### Onshape mode

- The selected Onshape document, workspace, element, and microversion are
  authoritative.
- CAD-Agent persists only an external resource link, immutable snapshots,
  Change Sets, execution state, verification evidence, and derived preview
  artifacts.
- Read operations may use the authenticated connector directly when they are
  bounded and audited. Every operation that can change Onshape must run through
  a dedicated Temporal workflow.
- Agent changes are prepared on a dedicated Onshape branch/workspace. The
  user's target workspace is not changed until the user accepts the preview.

### Guest mode

- Guest output is generated by the same Durable Agent V2, container runtime,
  validation gates, and preview pipeline as a registered native project.
- No static model, hard-coded result, or frontend-only parameter change is a
  valid guest experience.
- Guest projects have explicit compute quotas and expiry. Registration may
  claim a project without changing its revision or artifact identities.
- External connectors, shared credentials, and high-risk exports are disabled
  for anonymous principals.

## Architecture

```text
Unified Mechanical Workspace
  -> CadSourceAdapter
       -> NativeCadAdapter
            -> McadAgentWorkflowV2
            -> ProjectRevision / Artifact
       -> OnshapeCadAdapter
            -> read-only connector queries
            -> OnshapeMutationWorkflow
            -> Onshape workspace / microversion
  -> immutable PreviewArtifact
  -> ParameterBinding[]
  -> ChangeSet
  -> task event subscription
```

`McadAgentWorkflowV2` remains the only native MCAD generation and modification
workflow. Onshape is an external CAD system, so its mutation lifecycle belongs
to a separate `OnshapeMutationWorkflow`. Both workflows reuse the existing
control-plane concepts: `WorkflowRun`, `StepRun`, `ExecutionAttempt`, task
events, durable confirmation, idempotency, audit, and WebSocket replay.

The Agent can choose a source adapter from explicit project context, but it
cannot call an Onshape write endpoint directly. Model-visible tools submit a
typed intent to the control plane; Temporal owns execution after submission.

## Data model

The names below are logical product contracts, not permission to create a
parallel connector schema. The implementation reuses and evolves the existing
`connector_tokens`, `connector_oauth_states`, `connector_records`,
`connector_links`, `connector_audit_records`, and `connector_artifacts` tables.
New columns or focused tables are added only where the existing request-oriented
records cannot enforce revision, workflow, or foreign-key invariants.

### `ConnectorAccount`

Is projected from the existing encrypted token and connector-record storage.
It stores tenant and principal ownership, provider, external user identity,
enterprise base URL or company context, granted scopes, status, expiry, and
references to encrypted credentials. Access and refresh tokens are never
stored in task events, prompts, artifacts, or ordinary audit payloads.

Token material must be encrypted using the deployment secret manager or KMS.
Each account has an owner principal, an explicit delegation list, an active
credential generation, and a lifecycle state. A project collaborator may use
the account only when both project permission and an explicit account grant are
present; project membership alone never delegates a user-owned OAuth token.

Refresh is serialized per account with a database lease and credential
generation CAS. A refresh journal is persisted before the provider call. The
new encrypted token bundle replaces the old bundle only with
`WHERE generation = expected AND status = active`, then advances the
generation. A crash after provider rotation but before local commit cannot be
made atomic across systems: an expired refresh lease moves the account to
`reconnect_required` rather than retrying an uncertain refresh token.

Every external request carries the expected account generation and rechecks it
immediately before dispatch. Disconnect or revoke increments the generation and
locally fences already-issued capabilities before best-effort provider
revocation.

The connector issuer and API base URL come from the registered OAuth
configuration and verified account metadata. Only HTTPS Onshape production or
explicitly configured enterprise Onshape domains are allowed. A pasted resource
URL supplies resource IDs only and can never select the outbound host.

### `ConnectorResourceLink`

Evolves the existing `connector_links` record from a publishing link into a
typed project-to-resource mapping. It maps a CAD-Agent project to a
user-authorized Onshape resource:

- connector account;
- document, workspace, and element IDs;
- external resource type;
- last observed microversion;
- access mode and capability snapshot;
- optional active Agent preview workspace;
- last successful synchronization time.

The resource link is tenant-scoped and protected by the same RLS model as
projects and revisions.

### `ParameterBinding`

Describes one parameter exposed in the unified drawer. Native bindings point to
a native parameter identity. Onshape bindings point to a feature ID, parameter
ID, binding generation, and source snapshot hash. It is a discriminated value
contract:

- `quantity`: canonical decimal-string magnitude in the declared canonical
  unit, display unit, source expression, minimum, maximum, and optional step;
- `boolean`: canonical `true` or `false` plus provider editability rules;
- `enum`: canonical provider value, display label, and the complete allowed
  value set observed by the supported adapter.

Every binding also records required/read-only state and adapter schema version.
Before and proposed values use sorted, versioned canonical JSON; binary floating
point and localized display strings never enter the request hash. Server-side
validation repeats type, unit, range, enum, generation, and snapshot checks.
The UI never constructs raw Onshape feature payloads.

### `ExternalRevision`

Records the observed Onshape microversion, source workspace, feature snapshot
hash, preview artifacts, origin workflow, and creation time. It is an immutable
local reference to external state, not a replacement for Onshape history.

### `ExternalChangeSet`

Onshape does not create a synthetic `ProjectRevision`. A separate external
aggregate owns connector state while the frontend consumes a common,
discriminated `EngineeringChangeSetView`:

- `source_kind=native` requires native revision and branch references and uses
  the existing native commit handler;
- `source_kind=onshape` requires connector account/resource/workflow references,
  forbids native revision references, and can be applied only by the Onshape
  workflow.

The external aggregate is tenant-scoped with RLS, but authorization also
requires account ownership or delegation. It records:

- target resource and expected microversion;
- affected feature and parameter bindings;
- before and proposed values;
- preview workspace and preview microversion;
- validation evidence and risk classification;
- target-application result and resulting microversion.

Its states are explicit: `planning`, `awaiting_preview_confirmation`,
`building_preview`, `preview_ready`, `awaiting_apply_confirmation`, `applying`,
`reconciliation_required`, `applied`, `rejected`, `stale`, `superseded`,
`cancelled`, and `failed`. Only `preview_ready` may advance to apply
confirmation, and only `applied` identifies a verified target microversion.
Each revision request creates a new immutable intent generation with its own
canonical request hash, before/after snapshot hashes, and preview workspace;
prior generations become `superseded` and remain audit evidence.

An unknown external commit transitions the active generation to
`reconciliation_required`, its StepRun to `reconciliation_required`, and its
WorkflowRun to `awaiting_reconciliation`. That generation cannot be cancelled,
applied again, or superseded by another writer to the same target. Durable
reconciliation may move it to `applied` when the exact resulting state is
proven, or back to `awaiting_apply_confirmation` when non-application is
proven. If neither is provable, it remains blocked for explicit user or
administrator reconciliation; abandoning local intent never claims that an
external write did not occur.

## Onshape connection flow

1. The user starts an OAuth authorization request containing a signed,
   single-use state value bound to tenant, principal, and return location.
2. The callback exchanges the code server-side and verifies the Onshape user.
3. Access and refresh tokens are encrypted and stored as one
   `ConnectorAccount`.
4. The user selects or pastes an authorized document/workspace/element.
5. CAD-Agent parses only resource IDs, uses the account's verified issuer, then
   verifies access and records a `ConnectorResourceLink`.
6. Disconnect revokes or invalidates local credentials and disables the link.

Production user connections use OAuth. Shared `ONSHAPE_ACCESS_KEY` and
`ONSHAPE_SECRET_KEY` remain limited to development, controlled migration, or
explicit administrative service-account use; they are not a user-connection
fallback.

## Onshape read and preview flow

1. Read the current workspace microversion and supported Part Studio features.
2. Convert supported feature parameters into typed `ParameterBinding` records.
3. Obtain a real display artifact from the referenced Onshape state and store
   it as an immutable, hash-verified `PreviewArtifact`.
4. Render that artifact through the existing Three.js workspace.
5. Mark unsupported feature types as inspectable but not editable. The UI must
   not expose an enabled control that cannot execute a real update.

A cached preview is valid only for its recorded microversion. A newer
microversion makes it stale and triggers refresh before modification.

## Onshape preview validation

The preview export is requested from the exact preview microversion, not the
moving workspace head. Its object, source microversion, size, and SHA-256 are
persisted before validation. Geometry loading, rendering, visual judgment, and
DFM reuse the existing durable validation capabilities and execute through
their declared `StepRun` and `ExecutionAttempt` boundaries.

The external Change Set declares which gates are required or advisory. A
`failed` or `indeterminate` required gate blocks `应用到 Onshape`; advisory
results remain visible as risk. The apply step rechecks that its selected
preview artifact and evidence belong to the active intent generation and have
not been superseded.

## Durable Onshape mutation flow

```text
submit typed Onshape change intent generation
  -> persist WorkflowRun and proposed Change Set
  -> read target microversion and feature snapshot
  -> reject or re-plan if expected state is stale
  -> durable confirmation to create an external preview
  -> create immutable pre-change version from the target
  -> create a Change-Set-owned Agent preview workspace from that version
  -> apply typed feature updates to the preview workspace
  -> read back feature state and resulting microversion
  -> export and verify preview artifact
  -> user accepts, rejects, or requests another modification
  -> re-read target state and require the exact expected microversion
  -> replay the same typed feature update to the target with provider skew rejection
  -> read back and verify target state
  -> persist resulting microversion, evidence, links, and audit
```

The first release does not merge the preview branch. Merge semantics operate at
tab/workspace scope and would make the approved diff larger than the typed
parameter intent. Instead, the workflow replays the exact, validated parameter
update against the target feature using the target's expected
`sourceMicroversion` and provider `rejectMicroversionSkew=true`. Any skew or
changed target snapshot is a conflict; the workflow creates no target write and
moves the Change Set to `stale`.

Every logical provider operation owns one `StepRun`. Each physical HTTP try for
that operation owns one `ExecutionAttempt` with
`execution_kind=external_http`; no parallel connector-only task lifecycle is
introduced. An Attempt has `pending`, `running`, `succeeded`, `failed`,
`cancelled`, or `unknown_commit` state. Temporal Activity retries create new
Attempt rows under the same StepRun and are fenced from completing an older
Attempt. A retryable failed Attempt leaves the StepRun running; a successful
Attempt completes it; exhausted failures fail it; `unknown_commit` moves the
StepRun and WorkflowRun into the reconciliation states above. The attempt
records the endpoint operation, target identity, request hash, provider request
ID when available, response classification, and timing, but never credentials.

The idempotency key includes the workflow, logical step, connector account,
resource link, intent generation, expected microversion, before snapshot hash,
and intended after snapshot hash. A successful provider response plus a
verified resulting microversion is `APPLIED`. After a lost response,
`NOT_APPLIED` is provable only when the target remains at the exact expected
microversion and the targeted feature matches the before snapshot. Any changed
microversion without a conclusive provider response is `AMBIGUOUS`, even if the
current value equals the requested value, because a human may have made the
same edit. `AMBIGUOUS` maps to `unknown_commit`, is never automatically retried,
and requires user reconciliation.

Every mutating provider operation has an operation-specific reconciler before
automatic retry:

- pre-change version creation uses a deterministic correlation token in its
  name/description and the exact source workspace microversion; one matching
  version is adopted, none permits retry, and multiple matches are ambiguous;
- preview workspace creation uses a deterministic correlation token and exact
  source version lineage; one matching workspace is adopted, none permits
  retry, and multiple or changed matches are ambiguous;
- feature update uses the before/after snapshots and expected/resulting
  microversions defined above;
- translation/import records the returned translation ID when received. After
  a lost create response, retry is allowed only if provider document history,
  elements, and connector correlation prove that no matching translation or
  element exists; otherwise it is ambiguous;
- cleanup deletion treats provider `404` as deleted. An existing, unchanged,
  workflow-owned resource may be deleted again; a changed resource is retained
  and marked ambiguous.

No later provider operation starts while its preceding mutation is unclassified
as applied or not applied.

Each intent generation owns one preview workspace created from its exact
pre-change version. It has one serialized workflow writer and a deterministic
name plus persisted external ID. A retry adopts that recorded workspace; a
revision request creates a new intent generation and workspace rather than
refreshing or mutating the prior preview. Before each write, the workflow
requires the last recorded preview microversion and feature hash; any external
preview edit makes the generation stale. Applied and rejected preview
workspaces enter explicit cleanup retention. Stale, failed, cancelled, or
unknown-outcome workspaces are retained for inspection until reconciliation
proves deletion is safe.

## Supported first release

The first Onshape editing release supports:

- listing authorized documents, workspaces, elements, and Part Studio features;
- reading current microversion and feature definitions;
- editing existing quantity, boolean, and enum parameters through typed
  adapters;
- generating an Agent preview workspace and preview artifact;
- explicit accept, reject, revise, cancel, and reconnect actions;
- applying an accepted Change Set and verifying the resulting Onshape state.

The first release does not support adding or deleting features, arbitrary
model-generated feature JSON, arbitrary sketch entity manipulation, complex
assembly-mate editing, cross-document writes, or concurrent Agent writers to
one target workspace.

## Existing write-path cutover

All current Onshape write entry points are part of the migration inventory:

- `POST /api/onshape/documents`;
- `POST /api/onshape/publish`;
- `onshape_create_document` in `/api/agent/tools`;
- `onshape_publish_step` in `/api/agent/tools`;
- all new feature-mutation tools.

In durable production, these endpoints either submit an Onshape workflow and
return its durable task identity or are disabled. `OnshapeService` write
methods become Activity-internal implementation details. Capability discovery
advertises no direct-write tool, and there is no process-local fallback.
Translation-status refresh remains a read from Onshape plus a transactional
local projection update; it cannot initiate another translation.

## Unified workspace UI

The existing mechanical workspace remains the shell:

- central Three.js preview;
- source badge: native, Onshape, or guest;
- current native revision or Onshape microversion;
- task status and reconnectable progress;
- right-side parameter drawer;
- Agent entry point;
- Change Set review;
- validation and export actions.

Parameter edits are staged locally in the form only. The primary action is
`预览变更`, not an immediate write. Native mode creates a candidate revision;
Onshape mode creates the current intent generation's Agent preview workspace.
Revising the intent creates a new generation instead of rewriting that
workspace. `应用到项目` or
`应用到 Onshape` appears only after a real preview and required validation
complete.

Loading, empty, stale, unauthorized, unsupported, failed, retryable, cancelled,
and successful states are explicit. Connector absence is a normal state and
must never block native or guest use.

## Error and conflict handling

- `401`: perform one controlled token refresh; `invalid_grant` disconnects the
  account and asks the user to reconnect.
- `403`: record insufficient Onshape access and perform no write.
- `404`: mark the linked resource missing or access-revoked.
- `409` or changed microversion: mark the Change Set stale and re-read/re-plan.
- `429`: respect `Retry-After` through Temporal retry policy.
- provider timeout or `5xx`: classify as retryable only after read-back proves
  that the intended write did not already land.
- unsupported feature or parameter: show a truthful non-editable state.
- preview generation failure: preserve the preview workspace and evidence for
  inspection; never apply the change to the target.
- target skew or provider microversion rejection: stop for user review and mark
  the intent `stale`; the first release never merges preview workspaces or
  silently selects a conflict strategy.

## Security and tenancy

- OAuth state is signed, single-use, short-lived, and bound to the initiating
  principal.
- Connector credentials are never exposed to the browser, LLM, CAD sandbox,
  Temporal history, WebSocket payload, logs, or artifacts.
- The Temporal Activity receives a short-lived credential capability or loads
  the encrypted token under its server identity at execution time.
- All connector rows include `tenant_id` and use RLS. Application roles remain
  non-owner and have no `BYPASSRLS`.
- Write tools require explicit user confirmation, project permission, account
  ownership or delegation, active credential generation, and resource-level
  access checks at execution time, not only at planning time.
- Connector callbacks, webhook endpoints, and redirect targets use allowlists
  and request validation.

## Guest lifecycle

Guest principals receive a 256-bit opaque, server-issued session credential;
only its hash is stored. It is delivered in a Secure, HttpOnly, SameSite cookie,
is revocable and rotated on security-sensitive transitions, and is required for
every guest project operation. Guest principals also receive strict quotas for
model calls, CAD runtime duration, storage, concurrent tasks, and retained projects.
Expiry is persisted and enforced server-side. Cleanup removes expired projects
only after active workflows are terminal and follows existing artifact
retention and audit rules.

For the first release, claim is supported only during signup. Each guest starts
inside its own provisional personal tenant. Claim proves both the unexpired
guest credential and the newly authenticated account, then performs a CAS state
transition `guest_active -> claiming -> claimed`, adds the authenticated
principal to the same tenant, and revokes the guest principal. `tenant_id`,
project, revision, artifact, workflow, event, and audit identities do not move.
Claim-aware signup receives and validates the guest credential before ordinary
personal-tenant provisioning, suppresses creation of a second tenant, and sets
the claimed tenant as the authenticated session's active tenant. If generic
signup provisioning has already begun, claim fails closed instead of trying to
merge two tenants.
Claim is rejected while a workflow is active or cleanup has started; cleanup
must CAS `guest_active -> expiring` before deleting anything. Existing accounts
cannot import an anonymous guest project in this first release; cross-tenant
copy/import is a separate feature.

## Deployment and cutover

Native Durable Agent V2 and its current preview can deploy independently of the
new connector. The existing STEP publishing UI remains labeled as publishing,
not editing, but its production write action must be routed through the durable
Onshape workflow before it is advertised. Otherwise the action is disabled.

User-owned Onshape editing stays behind a server-side capability flag until all
of the following are true:

1. the production OAuth application, redirect URLs, and required permissions
   are configured;
2. migrations, RLS policies, token encryption, and revocation are verified;
3. the Onshape Temporal worker and activities are ready before API capability
   advertisement;
4. real-account integration tests pass against a dedicated Onshape test
   document;
5. restart, stale-microversion, duplicate submission, timeout reconciliation,
   and token-refresh tests pass;
6. the frontend displays editing only when the authenticated connector reports
   the required capability.

No request falls back from the durable workflow to direct Onshape writes.
Rollout is capability-based per tenant/account, not a second product path.

## Verification

Release evidence must include real calls using a dedicated non-production
Onshape account and disposable documents. Unit fakes are useful for error
classification but do not count as connector release evidence.

Required scenarios:

- OAuth connect, refresh rotation, revoke, reconnect, and enterprise base URL;
- document selection and permission rejection;
- real feature read and quantity/boolean/enum modification;
- preview workspace creation, preview rendering, accept, reject, and revise;
- concurrent human edit between planning, preview, and apply;
- API `401`, `403`, `404`, `429`, timeout, and `5xx` behavior;
- FastAPI and Temporal Worker restart during each durable phase;
- duplicate submission and unknown-write reconciliation;
- tenant isolation, audit redaction, and credential non-disclosure;
- native registered project and real guest generation regression;
- real signup claim with ID preservation, guest expiry, cleanup race, duplicate
  claim, revoked credential, and cross-principal rejection;
- desktop, tablet, and mobile workspace behavior.

Deterministic provider-failure coverage uses a test-only forwarding proxy
between the connector worker and a dedicated Onshape test account. The proxy
can reject before forwarding, delay, return controlled `429`/`5xx`, or forward
a real write and drop only its response. Tests still verify the resulting real
Onshape microversion and feature state; pure response stubs do not count as
release evidence.

## Acceptance criteria

- A user without Onshape can generate, preview, adjust, validate, and export a
  real native model.
- A guest sees a real Durable Agent V2 result, not mock content.
- An OAuth-connected user can open an authorized Onshape Part Studio in the
  same workspace, preview its current state, and edit supported parameters.
- No Onshape target workspace changes before confirmation and successful
  preview.
- An accepted Onshape Change Set produces a verified new external
  microversion, visible in Onshape and referenced by durable local evidence.
- Browser disconnect, API restart, Worker restart, retry, and duplicate
  submission do not lose the task or repeat an already-landed write.
- Unsupported editing capability is disabled and explained, never simulated.

## External dependencies and risks

- Onshape OAuth application registration, distribution approval, scopes, and
  API quotas may control launch timing independently of code readiness.
- Onshape feature representations are provider contracts and may evolve;
  adapters must be API-versioned and validated against live fixtures.
- Preview branching and target replay add latency and may encounter user
  changes.
  This cost is accepted to avoid silently corrupting a target workspace.
- Geometry identity can change across microversions. Long-lived UI bindings
  use feature and parameter identities plus snapshot hashes, not face or edge
  IDs as permanent product keys.

## Out of scope

- Real-time cursor-level collaborative editing inside Onshape.
- A permanent warm Onshape session.
- Fusion 360 or other connector implementations.
- Replacing Temporal, `ExecutionBackend`, native `ProjectRevision`, or the
  existing Three.js viewer.
